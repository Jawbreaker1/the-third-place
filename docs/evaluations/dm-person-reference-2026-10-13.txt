Isolated DM person-reference experiment — 2026-10-13
===================================================

Decision: PARKED, NOT ACTIVATED
------------------------------
The separate semantic person resolver did not demonstrate a robust improvement.
V1 regressed; one generic prompt-only revision recovered aggregate accuracy but
introduced new language/candidate-order failures. No production integration was
made. The existing DM public-memory projection remains exactly as it was at the
start of this experiment. Nothing in the broader router, memory retrieval,
research selection, writer, reviewer, publication or queue was changed this turn.
Server and ngrok remained stopped. No real accounts or messages were created.

The candidate and its tests are retained only in:
  scripts/experiments/dmPersonReference.ts
  scripts/experiments/dmPersonReference.test.ts
The dedicated evaluation harness is:
  scripts/dm-person-reference-live-eval.mjs
  scripts/dm-person-reference-live-eval.node-test.mjs
No server module imports the experiment. The temporary compiled resolver was
removed from dist-server after parking; production builds exclude experiments.

Question and scope
------------------
Would separating third-person identity resolution from the existing broad DM
classification reduce wrong or lost references, without changing other semantic
decisions? The experiment deliberately stopped at identity selection. It did not
claim to improve final replies or solve unsupported private-history assertions.

The candidate accepts only the current DM pair's bounded message context and a
public-only identity inventory. It returns matched/ambiguous/unknown/not_applicable.
A match contains at most two supplied IDs, a literal source-message excerpt and
a literal current-message excerpt. Existing 0.9 confidence threshold is retained.
The parser validates data provenance, boundedness and membership, NOT semantic
identity truth. Unit tests explicitly demonstrate that limitation. No natural-
language regex, approximate-name algorithm or per-language/person rule was added.

Fixed comparison
----------------
Model: google/gemma-4-26b-a4b through the configured LM Studio backend.
One sequential evaluation lane; no concurrent app traffic from this project.

29 fixed scenarios, twice per variant:
  - The original eight DM-public-memory fixtures, with their archived router input.
  - The original explicit external-lookup control.
  - Ten previously held-out broad-classifier controls, unchanged.
  - Ten predeclared identity controls: unknown/similar handles, candidate order,
    contextual reference, correction, resident address, duplicate labels and Arabic.

The baseline executes real LmStudioClient.analyzeTurn, including its existing
verifier/recovery. The candidate executes only the narrow pure prompt/schema/parser
through the production model backend. Expected labels and rationales never enter
model input. No memory stores, web providers, writers or reviewers are invoked.

The archived transportLanguageHint:null is explicitly normalized to omission for

input. The original ambiguous-Alex catalog stays filtered exactly as archived.
The additional duplicate-label case is not baseline-supported: the old input schema

token budget, fixtures, settings and expected outcomes remained unchanged. The
revision frames identity linking independently of memory relevance/request intent
and clarifies that community display names may be handles. It adds no named example
or language exception. No further tuning was performed after V2.

Results — common 56 supported inputs
-----------------------------------
                        Correct   Wrong identity sets   Missed matches
Existing broad router     52              2                    2
Separate resolver V1      47              0                    9
Separate resolver V2      52              0                    4

The wrong baseline cases retain both the mistaken and corrected person in the
Japanese correction, twice. The two baseline omissions occur when broader evidence
plan recovery loses the person in an explicit external-source request. Baseline
still chooses web_search there; this table grades identity, not capability execution.

V1 omissions: Swedish public reference once, Portuguese order A/B four times,
Japanese correction twice, external attribution twice. Its total is 49/58 when
including the two correctly abstained duplicate-label cases.

V2 fixes the original Swedish miss, external-attribution omissions and Japanese
correction. However, it misses a direct Arabic reference twice and the Portuguese
order-A reference twice. Order B resolves the same Portuguese person correctly in
both repetitions. Input/settings verification confirms that this difference is
candidate-order sensitivity, not a different question or seed. Total including
duplicate-label controls is 54/58. That must not be compared to baseline 52/56 as
if the denominators were the same.

V2 identity-only groups:
  Original eight scenarios: 16/16 (baseline also 16/16).
  Explicit external control: 2/2 (baseline 0/2 identity, 2/2 final web_search).
  Existing nonidentity controls: 20/20 no unrelated IDs (baseline also 20/20).
  Comparable new identity controls: 14/18 (baseline 16/18).

All candidate outputs were complete, schema-valid and within deadline. Their
misses are semantic abstentions, not truncation, timeout or parser failure.
All 20 V2 matched resolutions were reparsed and their anchors manually inspected;
they selected the expected identity. No private sentinels appeared in input/output,
but this is NOT an end-to-end private-memory leakage test: there are no memory
stores or publication stage in this narrow experiment.

Mean/median isolated latency on the common inputs:
  Baseline: 3,981 / 4,003.5 ms
  V1:         571 /   444 ms
  V2:         610 /   459 ms
These are different-sized jobs. A future integrated resolver would run IN ADDITION
to broad routing; the figures are not a claim of faster complete DM conversations.
Two low-temperature repeats and duplicated order controls are a small diagnostic
sample, not independent production accuracy estimates or a guarantee.

Why not keep V2 active?
----------------------
Avoiding wrong identities is valuable. But equal aggregate accuracy hides four new
omissions in cases the baseline handled, including sensitivity to arbitrary catalog
order. That fails the requested non-regression bar. Do not patch these failures with
specific handles, language branches, string matching or a fallback to old guesses.
Keep the evaluation evidence; leave the application behavior unchanged.
